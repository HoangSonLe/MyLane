# AI Development Workflow

Version: 1.0

This document defines how AI tools should be used throughout the development of My Lane, and stores the reusable prompts for each step.

The objective is to ensure every generated screen, component and feature remains consistent with the project architecture and Design System.

# Step 1 - Generate Base UI with v0.dev

## Objective

Create a visual prototype quickly.

Focus only on:

- Layout
- UX
- Component composition
- Visual hierarchy

Do NOT focus on:

- Folder structure
- State management
- Accessibility
- Performance
- Code quality
- Reusable architecture

The generated code is considered a prototype.

## Prompt

```text
You are designing a mobile-first web application.

Generate only the visual UI.

Do not optimize code architecture.

Do not create reusable components unless necessary.

Focus on layout, UX and visual consistency.

The output is a prototype that will later be refactored by Claude Code.
```

# Step 3 - Claude UI Audit

## Objective

Analyze the generated code before refactoring.

Do not modify code yet.

## Prompt

```text
You are a Senior Frontend Engineer.

The UI inside this folder was generated by v0.dev.

Treat it as a visual prototype.

Do NOT redesign it.

Analyze the implementation.

Report:

- duplicated JSX
- reusable components
- accessibility issues
- responsive issues
- inconsistent spacing
- inconsistent typography
- hardcoded values
- maintainability problems

Do not modify the code.

Wait for approval.
```

# Step 4 - Claude Production Refactor

## Objective

Convert prototype code into production-ready architecture.

## Prompt

```text
You are a Senior Frontend Engineer.

Treat the current UI as the visual source of truth.

Preserve:

- layout
- spacing
- hierarchy
- UX
- interactions

Do NOT redesign the interface.

Your tasks are:

1. Extract reusable components.

2. Organize folders.

3. Improve TypeScript.

4. Improve accessibility.

5. Improve semantic HTML.

6. Remove duplicated JSX.

7. Replace hardcoded values.

8. Improve maintainability.

9. Follow the project architecture.

10. Follow the Design System.

Visual changes should be minimal.

Explain every visual change.
```

## Code Organization Rules

When refactoring generated screens or existing pages, follow these placement rules:

### Components

- Keep page files focused on orchestration.
- If a page contains many local subcomponents, split them into separate files as soon as they have a clear responsibility.
- Prefer folder-per-kit organization instead of one flat UI folder.
- Keep related components together under a dedicated kit folder such as `button/`, `card/`, `layout/`, `controls/`, `grid/`, `form/`, `settings/`, or a feature kit folder like `gameplay/`, `leaderboard/`, `profile/`, `result/`.

### Types and Enums

- Move shared enum-like values into `frontend/src/configs/enum.ts`.
- Do not create many feature-local `enum.ts` files if the values are shared across screens.
- Place feature-specific interfaces in separate files such as `xxx.interface.ts`.

### API and Mock Data

- Place feature API logic in `xxx.api.ts` or in a feature data-layer file when it is clearly not UI code.
- Place mock data in `xxx.mock.ts` or a feature-local `mocks/` folder.
- Do not keep API stubs, mock data, and UI markup in the same page file when the page is already dense.

### Refactor Priority

1. Extract repeated page shell and header patterns.
2. Extract repeated cards, rows, filters, and overlays.
3. Split dense page-local subcomponents into separate files.
4. Move shared enums, interfaces, API helpers, and mocks out of page files.
5. Keep the visual result unchanged unless a minimal fix is required.

For a general (not v0-import-specific) version of these placement rules, see [`ai-coding-rules.md`](ai-coding-rules.md).

# Step 5 - Component Extraction

Claude should gradually build reusable components.

Examples

```text
components/
  ui/
    Button
    Card
    Dialog
    Toast
    Badge
    Chip
    Progress
    Input
    Avatar
  game/
    GameBoard
    SequenceGrid
    MemoryCard
```

Avoid duplicate components.

## Prompt

```text
Claude should gradually build reusable components.

Extract shared UI and game components only when duplication or repeated patterns appear.

If a page contains many local subcomponents, split the subcomponents into separate files instead of keeping everything in one page file.

Prefer folder-per-kit organization rather than one flat components folder.

Move shared enums, interfaces, API helpers, and mock data out of page files when they start making the page hard to read.

Avoid duplicate components.
Keep the visual result consistent with the existing prototype.
```

# Step 7 - Future Screens

Whenever creating a new screen, reuse existing components.

## Prompt

```text
Create a new screen using ONLY the existing Design System and reusable components.

Do not introduce

- new colors
- new spacing
- new typography
- new button styles
- new card styles

If a new component is required,

extend the closest existing component.

Maintain complete visual consistency.
```

Concrete, per-screen versions of this prompt (Purpose, User Goal, Components, Data, States, Navigation — no style direction) for all 11 screens built for Version 1 are archived at [`archive/v0-screen-prompts.md`](archive/v0-screen-prompts.md); reuse that structure as a template for any new screen.

# Rules

Never let AI redesign the project automatically.

Never replace the Design System.

Never introduce a second visual language.

Always evolve the existing system.

Prototype first.

Architecture second.

Production third.
